## 3. 逻辑正确性（L1–L6）

| # | 发现 | 严重度 | 处置 |
|---|---|---|---|
| L1 | **面③ 最小版漏写"未知方法透明转发"**：第三方 UI（如 goose desktop）连 fleet serve 后必调 `goose.*_unstable` 扩展；若 fleet 只实现标准面，这些调用失败——passthrough 必须是**方法级透明代理**（未知方法原样转发，-32601 由节点语义决定，D7 复用） | **高（成立前提）** | 已补 HUB v0.2 §2 |
| L2 | **会话生命周期未定义**：client 断连时节点会话怎么办？未定义即不可实现 | 高 | 已补：镜像节点语义（断连即清理，与壳逐窗同构）；跨断线恢复归 P12 |
| L3 | "五形态走同一契约 1"措辞错误：stdio 进程形态根本不走 WS 契约——统一发生在**驱动抽象层**而非协议层 | 中 | 已勘正 notes v1.2 §6 |
| L4 | **嵌套舰队 hop 只能 advisory**：ACP 无 hop 字段，`_meta.fleet` 扩展仅 fleet 系客户端会带——异构客户端无法强制；真实防线是服务端深度上限 | 中 | 已补 HUB v0.2 §7 |
| L5 | standalone 桥直读 settings.json 与运行中 Electron 内存态有一致性窗口 | 低 | 已补 HUB v0.2 §7（attached 为正解） |
| L6 | 多面同节点并发（3 窗 + 桥 + 面③ = 5 连接）——核对成立：goose serve 多会话、dsh 每连接一进程，均天然支持，无冲突 | 无（正面确认） | 不需动作 |

## 4. 可落地性（F1–F4）

| # | 发现 | 处置 |
|---|---|---|
| F1 | **M2 估时缺失且被低估**：原稿"最小版"读起来像薄代理，实际含扩展透明转发、会话生命周期、断连语义、权限转发——**2–3 周**不是 2–3 天 | 已补 HUB v0.2 §6 估时列 |
| F2 | **V1 是硬前置**：面③ 的唯一非自有消费者（dsh-orchestra/dsh-fleet web 的 ACP client 能力）从未核实——若两者都不是 ACP client，M2 判据只剩 goose desktop 一个客户 | HUB §6 已有 V1；本评审升格为 **M1 开工前置** |
| F3 | M0 可落地性最高：mock ACP 先例、常驻桥 :3284、goose 二进制、MCP SDK 全部现成 | 不需动作 |
| F4 | fleetd "L0/L1 只有一份实现"的承诺，靠的是 **fleetd-as-library**（同一份代码三种宿主：Electron 内嵌/桥进程/独立 daemon）——设计未明说这一点，是双实现漂移风险的解药 | 建议 HUB 后续版本显式化（未改，留给正式版） |

## 5. KISS（K1–K4）

- **K1 做对了**：passthrough 先于聚合（P12）；复用契约 1 server 侧而非新协议；P13 双形态不强制迁移；桥 standalone 零依赖试点。
- **K2 过度**：面⑤ TUI/CLI 是纯想象，设计里应删（保留 roadmap 一句话即可）；事件总线 M3"多面同看一个会话"无需求来源。
- **K3 五面表述**制造了"要建五个面"的观感——实际 v1 只需 2.5 个（①已有、②桥、③最小）；
  建议后续把④⑤标为"规划位，非交付项"。
- **K4 权限中枢**把三套已设计机制（桥策略引擎/手机挂起队列/OC 三重门）合流——方向对，但 v1 实现应取最小交集（单策略引擎 + 事件扇出），OC-N1 两步配对**不进 M1/M2**。
